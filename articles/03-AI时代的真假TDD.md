# ③ AI 时代的真假 TDD

> 系列文章 3/8 · 人工智能编程技能库应用方法
> 源材料：Matt Pocock Skills（github.com/mattpocock/skills）中测试驱动纪律的 AI 场景适配

## 一、"先把测试全写完"为什么是假的

经典 TDD 的信仰版本：先写全部测试，再写实现，测试先行保证实现不偏航。在 AI 生成代码的场景下，这个版本有三处系统性失效：

1. **AI 可以同时读测试和实现，"先写"失去约束力**。人类 TDD 的约束力来自信息隔离——写实现的人看不到测试答案（或测试就是规格本身）。AI 没有信息隔离，你让它"先写测试"，它写的是它**预期会写**的实现对应的测试——测试与实现同源共谋，一起错。
2. **测试写得比实现快**，但测试的"正确性"依赖对实现的假设。实现一旦和假设不符（AI 经常不符），整批测试一起重写，先行成本变成沉没成本。
3. **批量测试没有反馈环**。红绿循环的价值在"每写一小步实现，立刻被一个红测试拽回来"。一次性写完 50 个测试再写实现，得到的是 50 红→全绿的黑盒跳跃，中间没有可归因的反馈。

所以"假 TDD"的判据只有一条：**测试是否真正在实现之前就锁死了行为**。AI 场景下，靠"先写"锁不住，必须靠"锁死的测试先于并约束每一步实现"。

## 二、真 TDD 在 AI 场景下的闭环：红绿循环的逐步版

正确的形态不是"先写完再实现"，而是**小步红绿循环，测试是每一步的验收锁**：

```
对每个行为（一次一个）：
  1. 写一个最小测试，描述这一个行为（规格粒度，不是函数粒度）
  2. 跑 → 必须红（红不起来=测试没测到东西，或行为已存在，回头检查）
  3. 让 AI 只实现这一个行为，允许它看这个测试
  4. 跑 → 绿
  5. 重构（AI 做，测试保持绿）
  6. 下一个行为
```

与假 TDD 的本质区别：

| | 假 TDD（全写先行） | 真 TDD（逐步红绿） |
|---|---|---|
| 测试数量节奏 | 一次性 N 个 | 一次 1 个 |
| 测试与实现的信息关系 | 同源共谋 | 每步测试先于该步实现 |
| 反馈粒度 | 黑盒跳跃 | 每步可归因 |
| AI 跑偏成本 | 整批重写 | 一步回退 |

**"红不起来"是最有用的信号**：测试写出来直接绿，要么是行为已存在（那本不该是这步），要么是测试根本没断言到位。AI 场景下这个信号尤其重要——模型经常顺手把测试也"修"了让它变绿。纪律：**实现步骤里，AI 不得改测试文件**；测试红了只能改实现，测试本身要改必须回到第 1 步重新走流程。

## 三、UI 场景：红绿循环失效在哪，替代方案是什么

UI 代码让纯 TDD 失效的原因：行为发生在**像素层和交互层**，而测试运行在没有像素的环境里。三种常见替代，按可靠性排序：

1. **行为测试下沉**：把 UI 的决策逻辑抽成纯函数/状态机（"购物车金额怎么算""这个按钮什么条件下可点"），对纯逻辑跑真 TDD，UI 组件本身只做薄绑定。能下沉的下沉，是收益最大的动作。
2. **快照+交互测试兜底**：对确实留在 UI 层的，用组件测试断言交互序列（点击→状态变化→渲染结果），不做像素断言。快照测试只防"意外变化"，不证"正确"——快照绿了不等于功能对。
3. **真实浏览器冒烟**：关键路径（登录、下单、支付）用 headless 浏览器跑端到端脚本，断言最终可观察结果。慢，但这是 UI 里唯一接近"真红绿"的东西。

纪律：三者混合使用，**纯逻辑必须真 TDD，UI 层不硬套红绿循环**——硬套的产物是大量"测了个寂寞"的组件测试。

## 四、集成场景：外部依赖让红变假

集成测试（真实数据库/第三方 API/消息队列）的失败往往是**环境问题**而非代码问题：网络抖了、mock 过期了、容器没起来。红绿循环在这里失效的方式是"假红"——测试红了，但原因是沙箱，改实现毫无意义。

替代方案：

1. **故障注入分级**：集成测试只跑"契约级"断言（接口形状、错误码语义），不跑完整业务流程；完整流程留给预发环境的冒烟。
2. **环境健康探针先行**：每次集成测试套件启动前，先跑探针（DB ping / API 探活），探针不过 → 整个套件标 SKIPPED 而非 FAILED。区分"环境红"和"代码红"是集成测试的第一纪律。
3. **AI 生成集成测试时的特别约束**：让 AI 生成集成测试时，必须先声明依赖清单（哪些服务、什么状态），运行器按声明起环境——AI 最常犯的错误是假设环境里"应该有"某个数据。

## 五、测试在 AI 工作流里的真实角色

把 TDD 从"信仰"还原成"工具"后，测试在 AI 辅助开发里的真实角色是三个：

1. **给 AI 的验收锁**：每一步实现的"做完了"由测试定义，不由 AI 自述定义（与文章⑧"不听实现者自述"同源）
2. **防漂移的回归网**：AI 重构/改需求时，回归测试是唯一能证明"没改坏别处"的机器证据
3. **给人看的规格文档**：测试套件是可执行的规格——新会话/新成员读测试比读代码更快知道"系统承诺了什么"

对应三条纪律：实现步骤 AI 不得改测试；环境红与代码红必须区分；测试粒度对齐行为而非函数。

## 六、小结

- 假 TDD = 测试与实现同源共谋的"全写先行"，AI 场景下约束力为零
- 真 TDD = 一次一个行为的小步红绿循环，测试先于该步实现，红不起来本身就是信号
- UI 层：逻辑下沉真 TDD + 交互测试 + 真浏览器冒烟，不硬套
- 集成层：探针先行区分假红，AI 生成的集成测试必须声明依赖清单
