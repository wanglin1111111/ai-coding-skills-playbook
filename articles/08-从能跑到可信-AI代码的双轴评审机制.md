# ⑧ 从"能跑"到"可信"：AI 代码的双轴评审机制

> 系列文章 8/8 · 人工智能编程技能库应用方法
> 源材料：Matt Pocock Skills（github.com/mattpocock/skills）中双轴评审设计 + 人工 Code Review 制度迁移

## 一、问题：AI 说"做完了"不等于做完了

AI 辅助开发的验收困境：**实现者会自述**。模型完成一轮生成后，会给你一份"我做了什么、为什么正确"的叙述——这份叙述不可信，因为：

1. 模型没有"知道自己错了"的可靠机制，错误实现配上自信解释是常态
2. "能跑"（测试过/无报错）只证明代码执行不崩，不证明它实现了你要的东西
3. 自述会选择性呈现——符合预期的部分讲得细，偏离的部分含糊带过

所以评审的第一原则：**不听实现者自述。**评审的输入只能是两个客观物：代码本身 + 规格本身。

## 二、双轴评审：两条独立的验收轴

"可信"需要两个独立维度的确认，一个都不能省：

### 轴 1：规格轴（Spec）——做的是不是要的东西

评审问题：实现是否与规格逐条对应？
- 规格里写的每一条，代码里找得到对应实现吗？（防漏做）
- 代码里的每个行为，规格里找得到出处吗？（防多做/自由发挥）
- 边界条件（规格里明确"不做"的）代码里真的没做吗？

规格轴的输入：**规格文档 + 代码 diff**。评审者不读实现者的解释。

### 轴 2：规范轴（Norms）——做得对不对

评审问题：实现是否遵守工程规范？
- 命名/术语是否符合 CONTEXT.md 术语表？
- 模块深浅是否达标（文章④的判据）？
- 错误处理/测试/日志是否符合团队规范？
- 安全基线（注入/越权/敏感数据）有没有踩？

规范轴的输入：**代码 diff + 规范文件**（CONTEXT.md、ADR、私有 skill 红线）。同样不读实现者的解释。

### 两轴并行的关键设计

1. **两个子 Agent 互不干扰**：机器评审场景下，规格轴和规范轴各跑一个独立 Agent，上下文互不共享——一个 Agent 读了另一个的结论，会被"先入为主"带偏（看到规范轴说"代码质量不错"，规格轴会放松警惕）。人审场景同理：两个 reviewer 分工，一人只盯规格，一人只盯规范。
2. **各自出结论，冲突时才仲裁**：两轴都过 → 可信；任一轴不过 → 打回；两轴结论矛盾（比如规格轴说"实现了"但规范轴说"这个实现方式本身就是错的"）→ 升级到人工仲裁，仲裁依据仍然是规格和规范的原文，不是任何一方 Agent 的自述。
3. **轴内子项可机器化**：规格轴可以半自动（规格条目 vs 代码符号的对应检查、"不做清单"的反向扫描）；规范轴大量可静态检查（术语表词频、接口宽度、红线模式匹配）。机器扫不出来的才上模型/人。

## 三、迁移到人工团队的 Code Review 制度

这套设计对人类评审会同样成立，迁移映射：

| 双轴评审（AI 场景） | 人工 Code Review 制度 |
|---|---|
| 规格轴 Agent | 指定一个 reviewer 只问"这是不是需求要的东西"，评审前只读需求单+diff，不读实现说明 |
| 规范轴 Agent | 指定另一个 reviewer 只问"写得规不规范"，只读规范+diff |
| 两 Agent 互不干扰 | 两位 reviewer 独立出意见再合流，先不互相通气（防锚定） |
| 不听实现者自述 | PR 描述限长（3-5 行）且只准写"改了什么+为什么"，禁止写"这是正确的因为……"；reviewer 对解释存疑时以代码实测为准 |
| 冲突升级仲裁 | 两轴结论矛盾 → tech lead 仲裁，依据需求单/规范原文 |
| 轴内机器化 | 规格对应检查+红线扫描交给 CI 脚本，reviewer 只看机器扫不出的 |

人工迁移的三个最容易走样的地方：

1. **"顺便"评审**：reviewer 被要求"既看需求又看规范"，实际两个都看个大概。纪律：分工写进 PR 模板（两个 reviewer 字段，各自职责标注）。
2. **自述回潮**：实现者在 PR 里长篇解释"为什么这样对"，reviewer 被说服跳过验证。纪律：解释与验证分离——解释可以写，但 reviewer 的打勾必须以"自己跑过/读过对应代码"为前提。
3. **仲裁靠职级**：结论矛盾时职级高的赢。纪律：仲裁必须引用规格/规范的具体条款，引不出来的一方观点不成立——赢的是文档，不是人。

## 四、"能跑"到"可信"的完整验收链

把双轴评审放进完整闭环，AI 代码的可信验收链是：

```
实现完成
  → 机器回归（测试套件，文章③的纪律：实现者不得改测试）
  → 规格轴评审（规格条目 vs diff，机器半自动 + 模型/人兜底）
  → 规范轴评审（规范文件 vs diff，静态检查 + 模型/人兜底）
  → 两轴合流：全过 → 合入；任一不过 → 打回（打回原因必须引用规格/规范条款）
  → 冲突 → 人工仲裁（引用条款裁决）
```

每一步的"过了"都由**外部工件**（测试/规格/规范）定义，没有任何一步依赖实现者自述——这就是"能跑"到"可信"的全部区别：能跑=执行不崩，可信=每个承诺都有外部证据背书。

## 五、小结

- 第一原则：不听实现者自述，评审输入只有代码+规格/规范
- 规格轴管"做的是不是要的东西"，规范轴管"做得对不对"，两轴独立、互不干扰
- 矛盾升级仲裁，仲裁依据条款不依据职级
- 人工迁移：PR 双 reviewer 分工、解释与验证分离、仲裁引条款
- 可信 = 每个承诺都有外部工件背书
